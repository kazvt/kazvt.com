# Host lock and authenticated private rooms (GitHub Pages)

## First deployment

1. Deploy all files from this patch together. Close all pre-patch host and player tabs. The previous v1 room protocol cannot verify a host; it is intentionally not accepted. No game scores, decks, round data, slot state or shop data are cleared.
2. Open `/rg/console/` (or `/rg/`). Create a **unique password** (any nonempty password up to 1024 characters is accepted; a long random password is recommended if publishing the site lock). Confirm it, leave Remember this browser checked, and unlock. Never reuse a GitHub, Discord, email or other account password. No passphrase is transmitted to a server.
3. **To deter other visitors to the public website:** in the unlocked console, select **DOWNLOAD SITE LOCK** and confirm. Commit the downloaded `host-access-policy.mjs` over `ramblegamble/host-access-policy.mjs` in your Pages repository and deploy it. Do not publish the plaintext passphrase. This file contains a salted PBKDF2-SHA-256 verifier (600,000 iterations), not the passphrase or a room key. The verifier is public and permits offline guessing, so a short password is easier to guess; a strong unique password is recommended. Until you publish it, any browser can enroll its own local lock and start an independent local game. This is intentional so the owner can set up a password without embedding a default one in public source. Preserve your customized policy file on subsequent patches. Once deployed, hard-refresh both host pages and test the prompt in a separate private browser window; Pages caching may take time to expire. Existing remembered grants for the same verifier remain valid.
4. Start the room as usual from either host page. **Send three new private invitations.** Their v2 format pins the host's public key; the old v1 links and offline packets are rejected. Each player can keep their new link for successive rounds. Their `/rg/player/` page does not ask for the host passphrase. `/rg/draw/`, `/rg/place/` and `/rg/sort3/` are unchanged.

## Using the lock

- `/rg/` and `/rg/console/` share the local lock profile and remembered unlock on the same origin and browser profile. Remember is selected by default; when unchecked, that particular unlock is session/tab-local. There is no global account or shared database. Opening a different browser profile requires unlocking it separately and starts an independent game.
- LOCK HOST is available on the arcade ready/pause menus and in the console. It invalidates remembered and session grants across host tabs, makes host controls inert, hides the display, and stops keyboard shortcuts from reaching the game. It does not unload already initialized game modules or deliberately stop the elected reader. Saved submissions and ongoing background round updates still work; unlocking reveals the current state. Any currently open game dialog is dismissed normally where possible. The lock is not a pause button or a rollback: an in-flight game action may finish.
- Initial navigation or refresh while locked requires the passphrase before loading the game or joining reader election. If all already-initialized host pages are closed or refreshed while locked, live networking pauses until an authorized host page loads. Keep an initialized page open if you need incoming submissions while controls are locked. STOP ONLINE ROOM is the separate action that stops the shared live room.
- Remembered unlocks are local convenience flags, not security tokens. Anyone with control of the host browser profile/devtools can bypass the UI and access its state. This is not intended to defend against physical access or compromised same-origin scripts.
- If you forget an unpublished local lock, remove only the site-storage keys `rg-host-lock-profile-v1`, `rg-host-lock-grant-v1`, `rg-host-lock-epoch-v1` (and corresponding session grant) with all host tabs closed; reopen to enroll. Do not clear all site data unless you intend to lose the saved game and private identity. If you forget a published lock, replace the public policy from your repository with `export const SITE_HOST_VERIFIER = null;`, deploy, reset the local lock keys as above, then enroll and publish a new verifier. No private key or token should be committed.

## What the multiplayer security actually does

Version 2 uses Web Crypto in an HTTPS secure context. A P-256 ECDSA signing key is generated in the host browser; the private CryptoKey is nonextractable and stored in IndexedDB (`rg-host-identity-v1`), shared by both elected-reader pages. The invitation pins the public key. If the identity is lost, new room credentials are necessary. Keys are not exported or sent over the network. A nonextractable key prevents ordinary key export but does not prevent malicious same-origin code from using it.

1. The player opens a trusted private invitation from the host, establishes a normal PeerJS WebRTC data channel, and sends a hello containing room ID, seat and fresh random nonce, **not the seat token**.
2. The host generates its own nonce and signs a domain-separated transcript containing room, seat, both nonces and the ordered host/player SHA-256 DTLS certificate fingerprints from the established PeerConnection SDP. PeerJS 1.5.5 exposes `DataConnection.peerConnection`. This channel binding prevents simple proof relay between connections with different certificates. Missing/ambiguous fingerprints or invalid proof fail closed, rather than falling back to plaintext token exchange.
3. The player verifies the signature against the pinned host public key and its own view of the connection fingerprints. Only then does it send a domain-separated HMAC-SHA-256 proof using its random 128-bit seat token. The raw token is not sent in live join or submission messages. The host checks the proof against the current seat credential. Fresh challenges prevent replay across reconnects. Unauthenticated clients receive no private hands or round state.
4. Once authenticated, the live connection is bound to its seat. The host reconstructs the authorized submission envelope from the connection identity, validates current credentials and round ID, and commits under the existing shared mutation lock. Existing hand membership checks, duplicate protection and persistence-before-acknowledgement remain in force. Reconnects and reader handoffs repeat authentication without changing the invitations.
5. If an invitation leaks, click **REVOKE / REISSUE** beside that player's link on either host page; confirm and send the replacement. Their existing live connection is closed, and old live proofs and offline packets are rejected. Other players keep their links and live connections. Accepted answers remain accepted; revocation does not undo a vote or prior answer. **REPLACE ALL ROOM INVITATIONS** rotates the room ID and all three tokens, reconnects the enabled reader, and invalidates all old links/packets. The persistent signing key is retained; this rotates room credentials, not the browser's signing identity.

Offline links and packets are still bearer credentials passed through trusted private DMs, with the raw token necessarily present in the offline packet. They are not live cryptographic host verification, and the round embedded in the link should be trusted only if received from the host. Import requires current room and token, valid round ID and valid answer. Use OFFLINE ROUND / IMPORT ANSWER or manual host entry if the signaling service, WebRTC, or channel binding is unavailable. If IndexedDB or secure Web Crypto itself is unavailable the secure room cannot be initialized; manual host entry still works after a successful host UI unlock where applicable.

## Boundaries

- GitHub Pages is static. The public HTML, JavaScript and assets remain downloadable; the published password verifier is a deterrent against casual access, not a server-enforced authorization boundary. Real access control needs a server/gateway or private hosting. Do not publish sensitive information in the static repository.
- Other browsers visiting `/rg/` cannot modify this browser's local game or become its elected reader. Only same-origin tabs in the same browser profile share the state and Web Lock. The trusted invitation establishes which host identity the player expects; a maliciously replaced invitation itself is not detectable. Someone with a valid seat link can still impersonate that seat until revoked.
- WebRTC encrypts data in transit with DTLS. The app's challenge-response strengthens peer identity, not availability. A party that knows a room ID may still try to occupy it or disrupt signaling. PeerJS Cloud, the CDN, browser/OS and site's origin remain dependencies. This is not a formal audited authentication protocol, anti-cheat system, protection against malware/XSS, or protection against a compromised device or repository. There is no VPS, database, additional account or TURN service.
- Test on the actual deployed HTTPS website: open both host pages, unlock once, start a room, join with a separate device, submit, lock host controls, confirm another submission still arrives, unlock, close the active reader, confirm reconnect, revoke one invitation, verify old link fails and replacement succeeds. Repeat for Berryblast and Red Handed. Check that a clean browser asks for the passphrase after the site policy is published. The automated tests cover protocol and mocked UI/transport behavior, not production PeerJS Cloud connectivity.
