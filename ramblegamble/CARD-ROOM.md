# Card room (GitHub Pages, no VPS)

The existing `/rg/` arcade is the host/audience display. Its Card Games host tab is now a nonmodal side panel; the table itself has a screen-facing, tabletop-anchored HUD. The private player route is `/rg/player/`. No accounts, database, migration, server, repository writes, or API keys are needed.

1. Unlock `/rg/` (see [HOST-SECURITY.md](HOST-SECURITY.md)); choose the card table and open HOST (or the Card Games host tab). Pick Berryblast or Red Handed. Add prompt/deck lists as usual.
2. Right-click the card table or a game card to open the host panel, then click **START ONLINE ROOM** on `/rg/` or expand **PRIVATE PLAYER ROOM / READER** on `/rg/console/`. Send the three **COPY LINK** links individually to Kaz, Faroe and Erin (private Discord DMs, not the public channel). The links carry a pinned host public key and bearer seat credentials. Live seat proofs never transmit the raw token. Do not display them in a stream. You can share them before starting a round.
3. Start the game. Each player opens their link on their device. Berryblast: type and press Enter or Submit. Red Handed: choose one of five private evidence cards and Submit. A confirmed submission is locked. The host sees progress; after all three accepted responses, the host can reveal anonymous answers one at a time or all at once. Use REVEAL NEXT / ALL on the audience HUD or `cards reveal` / `cards all` in the console. Voting opens only after every accepted answer has been revealed. LOCK ANSWERS optionally ends submissions early if at least one answer was accepted. Existing audience voting and results still work. Next rounds arrive on the same connection.
4. Keep at least one host page open and awake. Both `/rg/` and `/rg/console/` in the **same browser profile and origin** share a room ID, seat credentials and round state via localStorage. One tab is elected ACTIVE READER using an exclusive Web Lock; the other shows STANDBY. Closing or navigating away from the reader releases the lock and the standby takes over automatically with the same invitation links. Players using live invitations reconnect automatically with backoff and resend unacknowledged submissions for the same round. There may be a brief interruption while the new reader registers or PeerJS releases the old peer ID. A suspended/frozen browser tab may delay handoff; close it if necessary. STOP ONLINE ROOM on either page stops live networking for both; restart from either page. When the room is enabled, reopening and unlocking either page resumes the election (remembered unlock is automatic). Locking already-running controls does not stop the room. The console can receive answers while `/rg/` is closed; reopen `/rg/` to display saved submissions. The existing game controls remain on `/rg/`.
5. Security upgrade: close all old-version host tabs, deploy all files together, and issue three new links. Version-1 invitations are intentionally invalidated; saved round and score data are not reset. The new room identity and host signing key are shared by both host pages. Both host pages must be on the same deployed origin (e.g. kazvt.com), not separate browser profiles or private windows. Web Locks requires a supported secure browser context; if unavailable the online reader is disabled rather than risking duplicate readers. The offline fallback remains usable with working storage.

See [PLAYER-SUBMISSIONS.md](PLAYER-SUBMISSIONS.md) for the current all-format submission workflow and private console answer viewer.

## Ending a table round

For Red-Handed, BerryBlast and Smeemo Scramble, **END ROUND** returns to the room and discards the round, including answers, cards, reveal progress and votes. Back navigation, switching to another machine, entering Dice or opening the pause menu from the table do the same. The table menu starts a new round with a fresh ID. Merely orbiting, using freecam, locking the host controls, losing a connection or closing a browser tab is not an explicit round exit. A superseding live trivia question keeps its existing lifecycle; leaving a shop display does not reverse purchases.

The reset uses the existing submission lock and verifies the abandoned round ID against current storage. It never writes the points or stars keys, alters authored decks, reissues invitations or cancels a newly started console round. Connected contestants receive the normal no-active-round snapshot and old submissions are rejected as stale. If persistence fails, the host receives an error and the menu retries before enabling a new selection.

## If live networking fails

Same-origin windows in the same browser profile/storage partition first try a SharedWorker rendezvous with a dedicated MessagePort per connection. This needs no signaling service or ICE and keeps payloads off the rendezvous worker. The existing signed host challenge and per-seat proof still apply, bound to a fresh local channel ID. Different devices/profiles use the pinned PeerJS 1.5.5 browser bundle (jsDelivr with cdnjs fallback) and the public PeerJS Cloud signaling service with WebRTC data channels. These are third-party services; direct peer-to-peer connectivity depends on network/firewall/NAT conditions. No guarantee of availability or relay coverage is made. There is no self-hosted signaling or TURN server and no hidden VPS requirement.

The room status separates local/remote readiness from the authenticated connected-seat count. A remote-ready reader is not proof that a contestant has connected. The player shows the current connection stage and offers Retry Now even during attempts; recoverable failures retry with backoff. A replacement tab for the same seat supersedes the old tab. Reload all host/player pages together after this update; existing v2 invitations remain valid. If remote connectivity fails despite retry, use the fallback.

The independent fallback works without PeerJS: after starting each round, use **OFFLINE ROUND** for each player and share that fresh link privately. It includes only that seat's prompt/hand. The player submits locally and copies the generated private packet into a DM; the host pastes it into **IMPORT ANSWER**. It is not accepted until the host imports it. Long offline links/packets may exceed chat message length; send them as a text file if necessary. Manual host entry is also retained. Live invite links are short and contain no hand or prompt; round-specific offline invites are longer. Old packets are rejected automatically.

## Trust and implementation

The v2 host verifies a per-seat HMAC proof after signing a fresh challenge bound to the connection’s DTLS fingerprints (remote) or a fresh dedicated local channel ID (same browser); the player verifies the signature against the host public key pinned in the trusted invitation. Offline imports validate the original bearer token. The host validates the 128-bit random room ID, current unique round ID, one accepted answer per player, max text length and exact membership in a Red Handed hand. The host sends each authenticated player only the prompt, its own evidence options, phase and submission status. It never broadcasts other hands, answers or scores to remote players. Browser-local state remains the original host storage; same-origin BroadcastChannel is not a cross-device network. The invitation is a bearer link, not a verified identity or strong anti-cheat system; anyone with that link can submit as that seat. Share it privately. If one link leaks, use REVOKE / REISSUE next to that player, then send the replacement privately. Other players remain connected; saved answers are preserved. REPLACE ALL ROOM INVITATIONS rotates the room ID and all three tokens and reconnects the reader. URL fragments are not sent in normal HTTP requests, but local browser history and whoever receives the link can see them. The public signaling service remains a dependency for cross-device availability; the CDN and website code remain trusted dependencies. The host lock is a UI deterrent rather than server authentication. See HOST-SECURITY.md for the threat model and deployment details.
