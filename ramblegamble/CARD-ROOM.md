# Card room (GitHub Pages, no VPS)

The existing `/rg/` arcade is the host/audience display. Its Card Games host tab is now a nonmodal side panel; the table itself has a screen-facing, tabletop-anchored HUD. The private player route is `/rg/player/`. No accounts, database, migration, server, repository writes, or API keys are needed.

1. Open `/rg/`, choose the card table and open HOST (or the Card Games host tab). Pick Berryblast or Red Handed. Add prompt/deck lists as usual.
2. Click **START ONLINE ROOM**. Send the three **COPY LINK** links individually to Kaz, Faroe and Erin (private Discord DMs, not the public channel). The links are bearer credentials for those seats. Do not display them in a stream. You can share them before starting a round.
3. Start the game. Each player opens their link on their device. Berryblast: type and press Enter or Submit. Red Handed: choose one of five private evidence cards and Submit. A confirmed submission is locked. The host sees progress; after all three accepted responses, the display automatically reveals anonymous answers underneath the Berryblast prompt or as Red Handed evidence cards. Existing audience voting and Reveal Results still work. Next rounds arrive on the same connection.
4. Keep one `/rg/` host tab open and awake; it is authoritative. If the host refreshes, start its online room again, and players click CONNECT / RETRY. Host room ID/seat credentials persist in sessionStorage for that tab, round/deck state in the existing localStorage. A new independent host tab may have a different room ID. Pending player submissions survive a refresh of the same tab until a matching round is acknowledged. Avoid operating multiple host tabs for card rounds.

## If live networking fails

The online path uses the pinned PeerJS 1.5.5 browser bundle (jsDelivr) and the public PeerJS Cloud signaling service with WebRTC data channels. These are third-party services; direct peer-to-peer connectivity depends on network/firewall/NAT conditions. No guarantee of availability or relay coverage is made. There is no self-hosted signaling or TURN server and no hidden VPS requirement.

The independent fallback works without PeerJS: after starting each round, use **OFFLINE ROUND** for each player and share that fresh link privately. It includes only that seat's prompt/hand. The player submits locally and copies the generated private packet into a DM; the host pastes it into **IMPORT ANSWER**. It is not accepted until the host imports it. Long offline links/packets may exceed chat message length; send them as a text file if necessary. Manual host entry is also retained. Live invite links are short and contain no hand or prompt; round-specific offline invites are longer. Old packets are rejected automatically.

## Trust and implementation

Host validates the 128-bit random room ID and per-seat tokens, current unique round ID, one accepted answer per player, max text length and exact membership in a Red Handed hand. The host sends each authenticated player only the prompt, its own evidence options, phase and submission status. It never broadcasts other hands, answers or scores to remote players. Browser-local state remains the original host storage; same-origin BroadcastChannel is not a cross-device network. The invitation is a bearer link, not a verified identity or strong anti-cheat system; anyone with that link can submit as that seat. Share it privately and open a new host tab for a fresh room if a link leaks. URL fragments are not sent in normal HTTP requests, but local browser history and whoever receives the link can see them. The public signaling/CDN services remain trusted dependencies for live play.
